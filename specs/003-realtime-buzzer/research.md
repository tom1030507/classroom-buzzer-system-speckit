# SF-03 設計決策

## HTTP 控制與 SSE 同步（FR-03、FR-05，AC-04、AC-09、AC-15）

活動控制和作答需要明確的伺服器回覆，採用 HTTP POST。即時更新從伺服器單向發送，使用原生 `EventSource` 重連並重新取得完整快照。每個連線只比對其授權範圍內的快照，相同內容不發事件，因此別組送出不會使學生串流出現可辨識的事件。輪詢整頁會反覆傳輸未改變的資料，WebSocket 則會為本功能引入未使用的雙向連線與額外管理。

## 交易序列與受理邊界（FR-03、FR-04、FR-08，AC-06、AC-07、AC-10、AC-18）

使用 SQLite `BEGIN IMMEDIATE` 的同步交易。受理操作在交易內重新讀取組別工作階段與活動階段，再驗證、去重、指定序號及儲存每一題。用教師結束與受理共用的交易順序判定競態。用戶端時間和伺服器時間戳都可能相同，`accept_seq` 才是唯一的受理順序。

`OPEN` 的有效重送回傳首次受理紀錄。#10 明訂結束生效後一律拒絕送出，`CLOSED` 的 POST 回 `409 INVALID_PHASE`，包含已受理單位的重送。遺失回覆時，可透過本組 GET 或 SSE 快照取回同一個受理識別與原答案。結束交易中的最終結果計算由 SF-04 #14 接續。

## 角色投影、題組內容與恢復（FR-04、FR-05、FR-08，AC-08、AC-09、AC-15、AC-16、AC-18）

教師取得各組的受理順序；學生只取得題號、活動資訊與本組的受理紀錄。學生識別使用 SQLite 產生且持久保存的隨機值，避免內部 ID 或序號透露他組紀錄數。送出端點以工作階段判定組別，檢查 Origin 與 CSRF，並在交易內按活動驗證作答單位；答案以 Unicode code point 計長，保留空格及換行，並以純文字呈現。保留資料庫時，伺服器重啟後仍能恢復本人已受理紀錄。

## 開啟前的匯入版本（FR-03，AC-04）

教師介面隨活動快照接收已確認匯入及其版本，開啟時帶回該版本。後端於狀態交易內比對目前確認內容，避免另一分頁換表後，舊畫面開啟不同題目或錯誤格位。證據見 [HTTP 整合測試](../../tests/integration/realtime-buzzer/realtime-buzzer.test.js) 與 [驗收紀錄](acceptance.md)。
